## 3. Controllers

### Api\Admin\SettingController
`index` (all settings), `show(Setting $setting)`, `update(UpdateSettingRequest, Setting $setting)`. **No authorization check at all beyond `auth:sanctum`** — any authenticated user (not just admins) can read and mutate every application setting including `auth.registration_open`, `auth.login_open`, `auth.protect_superadmin`, etc.

`show` → `GetProfile` action → `ProfileResource`. `update(UpdateProfileRequest)` → `UpdateProfile` action.

`show`, `update(UpdateUserSettingRequest)` — timezone/locale/theme/date & time format/meta.

### Api\Setting\TimezoneController
`index` — public, lists `Timezone` rows (used by register form + settings form).

### Api\Chat\ConversationController / MemberController
Full CRUD + pin/unpin for conversations; add/remove members. ### Api\Chat\MessageController
Completely empty (`// `), not registered in routes. Dead file.

### Web\Blade\AuthPageController
`index(Request, ?string $token)` — derives `$currentPage` from the request path via a `match(true)` and renders `blade.pages.auth.index` with `currentPage`, `resetToken` (route param), `resetEmail` (query string `email`). - **Identity/Organization** — `Department` model exists (`belongsTo`/`hasMany` wired on both sides, `isBanned()` via same Ban polymorphism) but **there is no `departments` table migration and no `department_id` column on `users`** — confirmed live: `Schema::hasTable('departments')` → `false`, and `users` table columns are only `id,name,email,email_verified_at,password,deleted_at,remember_token,created_at,updated_at`. ## 8. Middleware

- `App\Http\Middleware\TrackUserSession` — updates/creates a `UserSession` row keyed by `session_id` on every request for an authenticated user. **Not registered anywhere** (`bootstrap/app.php` only appends `AddLinkHeadersForPreloadedAssets` to the `web` group) — dead code. Also note it writes to a `session_id` column that isn't in `UserSession::$fillable` (`user_id, personal_access_token_id, ip_address, user_agent, device_name, device_type, browser, platform, logged_in_at, last_activity_at, logged_out_at`) — would mass-assignment-fail even if it were wired up.
- `auth:sanctum` — Laravel/Sanctum's stock guard middleware, applied per-route-group as shown in §1. Config: **no `config/sanctum.php` exists** (never published) — Sanctum runs on package defaults (stateful domain detection off unless configured; token guard `sanctum` from `config/auth.php`).
- No `guest` middleware anywhere (nothing stops an authenticated user from re-visiting `/login`/`/register`).
- No `verified` middleware anywhere (email verification, even if implemented, is not currently enforced on any route).
- No CSRF/Sanctum stateful-domain issues observed for the web layer — Blade forms use `@csrf` (session-cookie based `web` guard), while the JS layer authenticates via **Bearer token stored in `localStorage`** (`resources/js/blade/axios/client.js` attaches `Authorization: Bearer <token>` from `localStorage.getItem('auth_token')`) — i.e. this app uses classic Sanctum **API tokens**, not the stateful SPA cookie flow, even though a session `web` guard also exists in parallel. Two different auth mechanisms coexist (session guard for Blade page loads/`@auth`, bearer token for the JS API calls) and are not unified — a page load knows the user is logged in via session, but the JS layer only knows via the token in localStorage; these two can disagree (e.g. after `session()->invalidate()` server-side, the token in localStorage is still valid until explicitly revoked, and vice versa).

## 10. Authentication / Authorization architecture — VERIFIED FLOWS

`config/auth.php`: default guard `web` (session + Eloquent `users` provider). No other guards defined. Sanctum's own `sanctum` guard is used explicitly per-route via `auth:sanctum` middleware, not as the app default.

### `AuthController` — actual code (full file read)
```php
login(LoginRequest)      // implemented
register(RegisterRequest) // implemented
logout()                  // implemented, auth:sanctum
me()                      // implemented, auth:sanctum
```
That's it. `forgotPassword`, `resetPassword`, `verifyEmail`, `resendVerification` **do not exist as methods on this class or anywhere else in the codebase** (`grep -rn "function forgotPassword\|function resetPassword\|function verifyEmail\|function resendVerification" app/` → zero hits).

**Live-verified** (via `php artisan serve` + `curl`):
- `POST /api/auth/forgot-password` → HTTP 500, `Error: Call to undefined method App\Http\Controllers\Api\Auth\AuthController::forgotPassword()`
- `POST /api/auth/reset-password` → HTTP 500, same shape, `resetPassword()`
- (by identical reasoning, `verifyEmail`/`resendVerification` will also 500 — not individually curl'd but code path is identical)

### `login` (`LoginUser::handle`)
1. Rejects if `auth.login_open` setting is false → `abort(403)`.
2. Looks up `User::where('email', ...)->with(['department.ban','ban'])->first()`; `Hash::check` password; on failure → `ValidationException` on `email` field with message `auth.invalid_credentials`.
3. Rejects if `$user->isBanned()` or `$user->department?->isBanned()` (department ban path is currently always-false, dead, per §6).
4. If `auth.allowed_login_role_ids` setting is a non-empty array, checks `$user->role_id` against it — **`role_id` is not a real attribute on `User`** (roles are many-to-many, no such column) — **this branch is a live bug that would throw** the moment anyone configures `auth.allowed_login_role_ids` to a non-empty array (currently seeded as `[]`, so dormant).
5. Issues a Sanctum token (`$user->createToken('auth')`), creates a `UserSession` row, returns `{user: AuthUserResource, token: plainTextToken}`.

### `register` (`RegisterUser::handle` → `CreateUser::handle`)
1. Rejects if `auth.registration_open` is false, or global/daily user-count caps are hit (`auth.max_users_count`, `auth.max_register_users_count`).
2. Creates the `User` + a `UserSetting` row (resolves timezone by name from request or `localization.default_timezone` setting, else falls back to `UTC`).
3. If `auth.email_verification_required` → `sendEmailVerificationNotification()`, else → `markEmailAsVerified()`. **Verified live via tinker that both calls work** even though `User` doesn't formally `implements MustVerifyEmail` — the trait's methods are inherited unconditionally from `Illuminate\Foundation\Auth\User` (Laravel's Authenticatable base already `use`s the `MustVerifyEmail` trait regardless of the interface) — so this is NOT a bug, despite the commented-out `// use MustVerifyEmail;` line looking suspicious. One real consequence: Laravel's stock `verified` middleware checks `$user instanceof MustVerifyEmail` (the interface), which is false here — so even if you added `->middleware('verified')` to a route it would never actually block anyone, since the interface isn't implemented.
4. Assigns the default role: reads setting key **`auth.default_role`** (`Role::USER` fallback) — but the seeder actually stores the key as **`auth.default_role_id`** — mismatch means this setting is never found by that key, and every new user silently gets the hardcoded fallback `Role::USER` ("USER") regardless of what an admin sets. Low-severity behavior bug (harmless today since the fallback is reasonable, but the setting is effectively non-functional).

### `logout` / `me`
Straightforward: `logout` revokes the current token + marks the `UserSession` row logged-out; `me` returns `ProfileResource` (roles+avatar eager-loaded).

### CONFIRMED auth flows that EXIST and work
- Register (email+password, with optional timezone) — works.
- Login (email+password → Bearer token) — works, subject to `login_open`/ban/role-allowlist checks above.
- Logout (revoke current Sanctum token) — works.
- "Who am I" (`/api/auth/me`) — works, returns roles/permissions/avatar/ban/settings.
- Own-session management (list/revoke sessions, revoke-others) — works, fully separate from the auth flows above but related.
- Password reset **database table exists** (`password_reset_tokens`, standard Laravel migration) — so a real forgot/reset-password flow is buildable without new migrations, it's just never been implemented in the controller/actions layer.

### CONFIRMED flows that DO NOT EXIST — do not build UI expecting a working backend for these without implementing them first
- **Forgot password / Reset password** — routes exist, controller methods do not. Must implement `AuthController::forgotPassword/resetPassword` (+ Actions, using Laravel's `Password` broker against the existing `password_reset_tokens` table) before any UI can work end-to-end.
- **Email verification (verify link + resend)** — routes exist, controller methods do not. `email_verified_at` column exists, `sendEmailVerificationNotification()` works and would queue Laravel's default `VerifyEmail` notification (check `MAIL_MAILER`/queue config before relying on it), but nothing currently handles the incoming signed verification link or a resend request.

## GAPS / QUESTIONS (read before building the frontend)

1. **Forgot-password / reset-password / verify-email / resend-verification are all dead routes (confirmed via live 500s).** Must be implemented (Actions + AuthController methods) before any frontend flow for them can work. The DB table (`password_reset_tokens`) and Laravel's built-in `Password` facade/broker are available and unused — this is a normal, low-risk implementation, not an architecture change.
2. **No "carrier" / "client" concept exists anywhere in the backend.** The brief's requested docs split (`/docs/carriers`, `/docs/clients`, `/docs/admins`) has no basis in the current role model (`SUPER_ADMIN`/`ADMIN`/`USER` only). Recommend clarifying with the product owner whether: (a) those docs should map to `SUPER_ADMIN`→admins and `USER`→clients with "carriers" deferred/out of scope for now, or (b) a real Carrier/Client domain needs to be designed first. Do not invent Carrier/Client backend entities without sign-off — that would violate the brief's own "don't invent APIs" rule.
3. **No route-level authorization exists at all** — no Policies, no Gates, no role/permission middleware alias registered in `bootstrap/app.php`. `Api\Admin\SettingController` (global app settings incl. `auth.protect_superadmin`) is reachable and writable by ANY authenticated user today, not just admins. If the frontend adds an "Admin" section, it must not rely on the backend to hide unauthorized actions from a non-admin — but more importantly, this is a real security hole worth flagging back before shipping an admin UI on top of it (minimally: gate `admin/settings/*` behind a role check server-side).
4. **`ConversationListResource` reads `$this->name`, but `Conversation`'s real column/fillable is `title`** — group/channel conversation titles will render as `null` in the list endpoint today (title works fine in `ConversationShowResource`, which correctly reads `title`). Small, contained backend fix.
5. **Chat has no message send/list endpoints** (`MessageController` is an empty stub, not routed). A conversation can be created and have members managed, but nothing in the API lets a user post or read a `Message`. If the frontend brief expects a working chat UI, this needs backend work first (new routes + a Request + Actions + a Resource) — sizeable, scope it explicitly with the user before building a chat UI that can't actually send messages.
6. **Two coexisting, unreconciled auth mechanisms**: session/`web` guard (used by Blade's `@auth`/`@guest` on page load) vs. Bearer token in `localStorage` (used by the JS API layer for actual data calls). A page can render as "logged in" via session while the JS layer has no/an expired token (or vice versa) — the frontend rebuild needs one clear source of truth for "am I logged in" client-side (recommend treating the token as authoritative for anything that hits `/api/*`, and using `/api/auth/me`'s success/401 as the real check on page load rather than trusting `@auth` alone for anything beyond initial nav rendering).
7. Minor/contained bugs worth fixing opportunistically while touching nearby code (none block frontend work, all low-risk, single-file fixes): `LoginUser` references non-existent `$user->role_id` (dead unless `auth.allowed_login_role_ids` is ever populated); `RegisterUser` reads setting key `auth.default_role` but it's seeded as `auth.default_role_id` (silently falls back, so registration still works, just not configurable); `Conversation` model's `avatar` relation method shadows its own `avatar` fillable column; `TrackUserSession` middleware is fully dead (unregistered) and would fail mass-assignment if it were ever wired up (`session_id` isn't fillable); `User::currentSession()` relation hard-codes `auth()->user()` inside its own definition, which breaks if ever eager-loaded for a user other than the currently authenticated one.
8. `Chat\GetConversationsRequest` exists fully-written but is never actually used by `ConversationController@index` (which takes a plain `Request`) — either wire it in or delete it; leaving it is confusing for anyone extending chat later.
9. `select.blade.php` (`components/blade/u-i/select.blade.php` + `App\View\Components\Blade\UI\Select`) was mid-removal when this audit started (a prior turn asked to "remove select" and was interrupted) — decide whether to finish deleting it or implement it like the other UI components before building any form that would need a `<select>`.
